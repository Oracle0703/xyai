## 4. 需要澄清但不构成本次合并缺陷的项

### 4.1 [开放问题] 新增 Ops 路由是否向子管理员开放

**性质：** 这是权限范围的产品与安全决策，不能仅凭“上游新增了路由”认定为合并遗漏。

**本地合同：**

- `backend/internal/server/middleware/admin_auth.go` 对子管理员调用 `service.CanAccessAdminRoute(...)`
- 未知 `METHOD + Gin FullPath` **默认拒绝**
- `admin.usage` 已放行一批 Ops 只读错误查询

**上游本轮新增并已进入 merge 的路由：**

```text
GET /api/v1/admin/ops/ingress-rejections
GET /api/v1/admin/ops/ingress-rejections/health
GET /api/v1/admin/ops/auth-cache-invalidation/health
```

**现状：** `backend/internal/service/admin_permission.go` 的 `AdminPermissionUsage` 中，Ops 相关规则仍只有：

```text
/ops/errors
/ops/errors/:id
/ops/request-errors
/ops/request-errors/:id
/ops/request-errors/:id/upstream-errors
/ops/upstream-errors
/ops/upstream-errors/:id
```

**当前行为：**

| 角色 | 新路由 |
|---|---|
| 全量 `admin` | 可访问 |
| 拥有 `admin.usage` 的 `sub_admin` | 会被权限中间件拒绝 |
| 当前前端 | 未调用这三条接口，不会产生现有子管理员页面回归 |
| 前端若后续把这些入口挂到子管理员可见页面 | 在没有显式授权前会返回 403，符合默认拒绝策略 |

**为何不能直接判为合并缺口：**

1. `backend/internal/service/admin_permission_test.go` 明确断言未知 GET 路由默认拒绝，这是既有 fail-closed 合同，而不是遗漏的旁证。
2. `admin.usage` 当前合同只明确覆盖 usage、Dashboard 聚合/排行和部分 Ops 错误只读接口，没有“所有 Ops/健康接口自动授权”的规则。
3. ingress rejection 聚合包含 `client_ip`、`user_id`、`api_key_id`；auth-cache health 暴露 outbox、Redis subscriber、lookup 和 invalid-auth limiter 等安全运行态。自动加入白名单会扩大已批准权限范围。
4. `frontend/src` 当前没有消费 `ingress-rejections` 或 `auth-cache-invalidation` 接口，现有子管理员工作流没有因此退化。

**建议：** 本次保持默认拒绝，不修改生产白名单；该边界已补充到 `llm-wiki/wiki/backend.md`。若产品后续决定向 `admin.usage` 子管理员开放，应作为独立权限变更，先确认最小披露范围，再补 `admin_permission.go`、权限测试和前端可见性测试。

### 4.2 [既有低优先级] `frontend/src/App.vue` 缩进混用

`onAdminPermissionDenied`、部分 `canAccessAdmin` 分支和 event listener 使用 Tab，周围代码为 2 空格。该内容在本地 `main` 与 merge 结果中完全一致，因此不属于本次冲突解决问题。可在后续独立风格整理中统一，避免污染本次只解决冲突的变更边界。
