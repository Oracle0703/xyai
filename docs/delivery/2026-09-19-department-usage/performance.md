## 优化与复验

- 显式物化选中用户、周期聚合及个人峰值，避免周/月导出的重复扫描。
- 授权摘要直接从同次个人峰值聚合选择全局 champion，减少第二次全量聚合。保留确定性并列次序与空页回退。
- 优化前诊断曾出现周/月接近 50 秒和摘要超过 3 秒；最终结果通过优化取得，未放宽超时或验收阈值。
- 测试源码：`backend/internal/repository/department_usage_performance_integration_test.go`。本机完整 EXPLAIN/计时日志：`.git/codex-department/performance-v3.log`；v1/v2 诊断日志也保留在该本机目录，不入库。
- 从 `backend` 运行：配置隔离库 `SUB2API_POSTGRES_ONLY_INTEGRATION_DSN`，设置 `DEPARTMENT_USAGE_RUN_PERFORMANCE=1`，执行 `go test -tags=integration -p 1 -count=1 ./internal/repository -run '^TestDepartmentUsagePerformanceIntegration$' -v`。Windows 缓存环境见 wiki/ops。

### 管理员接口前后比较

同一测试源码分别运行于首版 `a9c53a9f6` 与本次修复树，600 用户/40 部门/600 订阅，ANALYZE 后每场景预热一次、顺序采样 50 次。p95 取排序第 48 项。两次使用同一隔离 PostgreSQL/机器；数据由同一夹具建立。本次未测 5,000 用户/200 部门，不作该规模承诺。

| 场景 | 中位数前 → 后 ms | p95 前 → 后 ms |
| --- | ---: | ---: |
| 部门列表 | 57.750 → 6.187 | 280.440 → 46.467 |
| 成员列表 | 4.500 → 4.345 | 8.248 → 21.862 |
| 订阅列表 | 10.398 → 9.555 | 57.364 → 69.283 |
| 订阅详情 | 8.629 → 5.070 | 22.483 → 9.536 |
| 单项重置 | 19.184 → 8.565 | 39.413 → 29.590 |

部门列表、订阅详情和单项重置有改善；成员列表及订阅列表的 p95 分别升至 21.862/69.283 ms，不能宣称所有尾延迟都变快。这两个新增诊断场景没有约定生产 SLA；上线后需按真实数据与负载监测。早期 10 样本及并行测试时的波动日志保留，以上统一报告 50 样本结果，不选择性删除较慢值。

查询次数验证：部门页大小 1 和 200 都为 4 次应用 SQL，成员页为 3 次，普通全站订阅 scope 为 1 次 actor 查询；计数不含事务控制。SQL 过滤/COUNT/LIMIT 与批量负责人/人数消除了随页大小线性增加的查询；小夹具 EXPLAIN 的顺序扫描不外推大表计划。全站报表生成摘要仍需装载实际选中成员，SQL 内摘要尚未采用。

可共享产物：[结构化计时](artifacts/rv-performance.json)、[实际 SQL 与 EXPLAIN](artifacts/rv-query-plans.json)。本机日志 `rv-report-performance.log`、`rv-admin-perf-50-before.log`、`rv-admin-perf-50-after.log`、`rv-pg-final.log`；测试入口 `department_usage_performance_integration_test.go`、`department_admin_performance_integration_test.go`、`department_query_count_integration_test.go`。两个性能入口均要求 `DEPARTMENT_USAGE_RUN_PERFORMANCE=1`。
