普通用户有保障 高用量按余量放行

先为普通组保留必要资源，再让高用量组充分使用共享余量。资源紧张时整组暂停，额度恢复后重新放行。

01 / 业务问题

分组已分开，资源仍在竞争

同一批上游账号的真实额度不会因为分组而增加。只限制个人频率，无法为普通组留下确定的可用资源。

当前模式

先消耗的人占用了后续使用空间

高用量请求持续进入同一个池子，普通任务可能在额度恢复前无法执行。

两个分组→同一个共享池→可能共同耗尽
推荐方向

先保障普通需求，再开放共享余量

高用量组仅在保护条件触发时等待，资源充足时继续正常使用。

明确保底→余量共享→暂停与恢复

03 / 实施机制

从资源分配到自动恢复

第一阶段使用已有分组绑定能力，第二阶段增加按分组执行的自动控制。

共享账号与普通组保底账号

现有能力可配置

保底账号必须具有独立的上游额度，并覆盖普通组实际使用的模型。高用量用户不能同时获得普通组权限或有效订阅，避免通过切组绕过。

每次新请求都经过分组保护判断

第二阶段拟建设

保护暂停作用于高用量组全部新算力请求，包含长连接后续轮次和重试。已经发往上游的请求允许结束，其消耗纳入安全余量。

持续监测与有条件恢复

第二阶段拟建设

额度数据不可信时，高用量组进入保护。普通组继续执行已有额度和账号健康检查。人工停用的分组不会被自动恢复。

04 / 关键规则

保障足够，限制适度

保底计算

按照后续真实需求预留

以普通组在额度恢复前的需求为依据，扣除独立保底账号已覆盖的部分，避免重复预留。

暂停与恢复

达到保护条件整组暂停

余量充足时正常使用。暂停后须超过更高的恢复线并持续稳定，才恢复高用量组。

计量范围

按真实资源分别判断

不同平台、模型及5小时或7天等额度窗口分别判断。费用金额和剩余百分比不能直接视为可互换算力。

共享池应预留的需求 = 普通组后续需求 − 独立保底已覆盖部分（最低为 0），再加入在途消耗与安全余量。

06 / 实施计划

先配置保底，再小范围启用自动机制

以阶段验收推进。工期和人力投入在平台范围、计量口径及入口清单确认后评估。

第一阶段 / 现有能力

让普通组先有独立保障

先解决共享资源耗尽时，普通任务没有资源可用的问题。

  • 盘点上游额度独立性、恢复周期及模型覆盖。
  • 配置普通组保底账号和共享账号。
  • 核对已有 Key、分组授权及有效订阅。
  • 验证共享额度耗尽与跨组访问场景。
完成条件：共享池耗尽后，普通组仍能在约定保底范围内使用。
第二阶段 / 新增自动控制

按余量暂停，再自动恢复

先观察规则是否准确，再选择一个平台的高用量组试点。

  • 建设额度监测、保护状态与用量记录。
  • 先记录拟暂停动作，覆盖相关恢复周期。
  • 统一 HTTP、长连接及重试的保护检查。
  • 验证自动恢复和回退后，再逐步推广。
完成条件：高用量组按规则暂停恢复，普通组不被连带阻断。
看保障效果普通组资源不足失败率与等待时长，是否符合事先约定的目标。
看资源效率共享池使用率、保底闲置率、高用量组等待时长和暂停后追加消耗。
保留回退能力自动机制可单独关闭，回到已验证的配置保底方案；人工停用优先。

建议先确认保障范围
并开展保底试点

先利用已有资源建立可验证的保障，再评估自动控制的研发投入。试点结果决定阈值调整和后续推广范围。

  1. 普通组需要保障到什么程度明确用户范围、关键模型、使用时段与需求量。
  2. 高用量组可以接受怎样的等待确认暂停范围、恢复规则和用户提示方式。
  3. 从哪个平台和分组开始试点约定验收目标、协同人员与回退条件。
