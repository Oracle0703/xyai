## 3. S1：权限版本与授权生命周期

### 3.1 两个写入口共用后端并发控制

**修复前 UI 起点（已修正）：** `UserEditModal.vue` 从列表行 `props.user` 初始化表单，没有请求用户详情；`handleUpdateUser` 每次保存都发送 role 和完整 `admin_permissions`。不能只在现有 payload 增加版本字段，就认为已避免旧快照覆盖。

1. 管理端用户详情返回不透明的 `admin_access_version`；按目标用户 ID、当前角色、规范化权限集合、排序后的 grant ID 集合生成。详情读取使用一致性快照，避免版本与表单内容来自不同状态；不把该字段扩散到公开资料、auth/me 或嵌套浅层用户 DTO。
2. `PUT /admin/users/:id` 显式提交 `role` 或 `admin_permissions` 时，必须携带 `expected_admin_access_version`；普通资料保存只提交已改字段，不夹带旧权限数组。用户创建仍是显式初始化，不要求已有版本。
3. `/admin/users/:id/department-scope` 保留 `expected_version` 字段名，值与上述共享授权版本采用相同规则。两个入口都在事务中按一致顺序锁定需要保护的用户行，读取最新角色/权限/grants、比较版本，再写入与审计；不能只在 service 预读后比较。
4. 缺版本返回 `ADMIN_ACCESS_VERSION_REQUIRED` (400)，不匹配返回 `ADMIN_ACCESS_CHANGED` (409)，无修改副作用。修改权限的旧 API 客户端必须补版本，不能为兼容而绕过检查；不携带权限/角色字段的资料请求保持兼容。
5. 字段版本仅是并发条件，操作者仍由可信登录身份与数据库最新权限鉴权。仅隐藏前端勾选项不能作为修复。

**用户编辑必须完成的两步：**

| 步骤 | 行为与验证 |
| --- | --- |
| 打开或切换用户 | 调用 `GET /admin/users/:id` 取最新详情与 `admin_access_version`；冻结未编辑的角色/权限基线。加载中禁止保存，失败不回退到列表旧数据；取消或切换用户时忽略迟到详情 |
| 保存差量 | 比较当前表单与详情基线，权限按集合比较而非数组顺序。仅当角色或权限实际变化时附带 role、规范化权限集合及 `expected_admin_access_version`；仅修改备注等资料时不发送这三项。409 刷新详情后重新确认，不自动覆写 |

后端仍检查任何显式提交的权限/角色字段及版本，不能仅依赖前端差量判断；权限发生变化时两字段与版本必须来自同一详情快照。

`admin.subscriptions` 与 `admin.department_subscriptions` 互斥；有 grant 不等于有部门订阅权限。显式配置“部门报表权限 + 全站订阅权限”的一般子管理员组合仍可保留，不把它标记为“仅限本部门负责人”。禁止的是过期请求隐式恢复权限；完整管理员携带当前版本明确调整权限的正常操作应继续支持。

### 3.2 降级和删除

- 用户离开 `sub_admin` 时，角色/权限更新、该用户持有的 grants 删除及审计同事务完成；重新提权不恢复旧范围。
- 用户软删除时同事务清其持有的 grants；保留其他负责人记录中的 `created_by`，软删除不会触发该外键的物理删除限制。
- 临时停用用户立即禁止管理访问，恢复后可使用原授权；不把停用等同角色降级。无 grants 的账号保留部门权限码时仍拒绝数据与重置，不退回全站。
- 清理与 `SetAccess`、转岗、额度重置共享并发保护，避免清理后被在途授权重新写回。未来物理清理须另行处理 `created_by` 等外键；当前不修改外键行为。
- 实施前只读检查是否有既有降级/软删除残留；如需清理，以追加迁移或可审计事务处理。不得改写已经应用的 239/240 migration。

## 4. S2：查询版本只反映本次范围

| 内容 | 处理 |
| --- | --- |
| 选项目录 | 两个 `/scope` 接口返回授权选项、默认筛选及 `catalog_version`；它只描述目录授权，不作为报表或订阅列表的 `scope_version` |
| 首次查询 | 按实际组织、部门、邮箱和平台筛选执行 Summary/订阅列表，首次可不传 `scope_version`；服务端同事务返回生效筛选和查询版本 |
| 版本输入 | 操作者当前操作所需的权限模式、本次有效授权交集、规范化筛选、选中成员的 ID/邮箱/组织/部门/成员版本、相关部门 ID/名称；固定排序后摘要 |
| 状态变化 | 先按 active/未删除口径选成员，启停/删除造成集合变化即改变版本；不能因删掉 status 字段而把这些变化漏掉 |
| 排除无关变化 | 不包含未选范围的成员/部门、未展示且不参与筛选的 username、纯排序/更新时间；不直接把包含排序修改的整个 `departments.version` 加入报表摘要 |
| 邮箱与部门名 | 参与筛选、标签及导出，变化需要检测；不得一概排除 email |
| 全站查询 | 全站新 active 用户改变成员集合，版本变化合理；仅查研发部时，新建无关部门成员不应影响该查询 |

页面先建立 Summary 快照，再用返回的 canonical `as_of/scope_version` 请求 Trend；翻页和趋势续查复用该快照。已加载页面导出携带当前成功快照；无既有快照时先以首个 Summary 建立，所有后续页及 Sheet 一致。页面遇 `REPORT_SCOPE_CHANGED` 最多重新建立快照一次；导出遇变化中止，不能拼接不同版本。

订阅列表版本按实际部门/用户等生效范围生成；筛选批量重置绑定最近成功列表的筛选与版本。选项目录版本不得塞进重置 payload 冒充列表快照；列表加载/失败立即使旧快照失效。订阅状态、过期与额度写入仍按原执行时条件检查，版本不冻结消费或订阅数据。

目录字段已改为 `catalog_version`，前后端和测试已同步；Summary/列表独立建立查询版本，不调整原无部门参数的全站订阅 API 兼容规则。

三个版本名称不得混用：`catalog_version` 是目录；`admin_access_version` 是被编辑用户的角色/权限/grant 并发版本；`scope_version` 是实际数据查询范围。目录版本不能进入权限编辑的 expected 字段，也不能代替列表/导出快照。

### 4.1 RV3 备选：按成员创建时间限定导出集合

默认合同保持当前成员口径，不启用额外创建时间限制。若需要降低开放注册对全站多页导出的干扰，可选择 `users.created_at <= canonical as_of`：

- Summary 首次确定 canonical `as_of`，人员选择、零用量人数、部门汇总、Trend、Periods、版本及全部导出页共用此上界；概览和 Excel 明示该成员限制，不只过滤人员表。
- 创建时间晚于上界的新注册不使已开始导出失效；已有成员停用、删除、转岗、邮箱和部门标签变化仍按实际影响检测。
- 回填旧创建时间的导入仍可能进入集合，该方案不是真正数据库快照，也不冻结迟到日志；不套用到订阅页或额度重置。
- 如采用，RV3 增补“新注册不中断、相关旧成员变化仍中断、页与汇总同口径、created_at 等于上界的包含边界”用例，并相应替换该方案下“新成员必导致失效”的预期。未采用时，不把备选用例作为必需门禁。

## 5. S3：SQL 查询与并发边界

| 路径 | 目标 |
| --- | --- |
| 部门管理列表 | SQL 内过滤组织/状态/搜索、count、稳定排序及分页；分页部门的人数、负责人批量聚合，查询次数不随页内部门数线性增加 |
| 成员列表/compact 搜索 | SQL 内过滤组织、部门、状态、搜索及显式用户 ID，再分页；不先把全站用户装入 Go 后切片 |
| 完整管理员/全站订阅子管理员普通订阅读取 | 验证最新身份和相应权限后，无部门筛选时不为部门授权加载全站成员；详情按主键读取，保留必要的事务一致性 |
| 管理员指定部门/未分配 | 直接添加部门、组织等 SQL 谓词；完整权限不意味着忽略用户筛选 |
| 部门负责人 | 由当前 grant 与用户归属构造授权 SQL；count、行数据、嵌套用户、compact 选项使用同一范围与快照 |
| 报表 | 权限、过滤和版本使用同一选中集合；查询或哈希确实需要全范围时允许必要聚合，但不为通用管理员订阅操作反复装载完整成员 DTO |
| 重置 | 必要的目标 ID 发现后按固定顺序加锁，锁内重新鉴权；复用当次解析结果，避免列表/详情/检查函数重复全量解析 |

保留 `users` 行锁协议，优先缩小锁集合到操作者与实际候选成员，并在锁内重新校验；发现新候选未锁定时返回范围变化，不扩大写入。单次成员分配上限 200 不代表部门人数或筛选批量重置上限，不能套用该数字限制原重置功能。

管理员可省去仅为部门限制而引入的全成员锁；权限、目标订阅、原子更新所需的锁仍保留，不能因 `role=admin` 无条件跳过全部锁或最新鉴权。覆盖角色/权限修改、软删除、停用和跨组织邮箱更新与重置的交互。

锁序必须显式记录：需要成员保护的重置先锁 `users`，再更新 `user_subscriptions`；计费仓储的写分支顺序是 `user_subscriptions`，再 `users`。当前 command 构造在订阅费用与余额费用间二选一，实际请求仅走一侧，因此这两条路径目前不形成该 AB-BA 双表环；仓储接口本身可同时表达两种费用，不能把入口互斥夸大为数据库强约束。

RV5 既要覆盖重置与余额扣费、撤权、转岗的真实 PG 并发，也要验证 command 二选一。未来增加混合扣费或同事务新增另一张表的写入时，必须先复核并统一锁序，再扩充用例；测试目标包括无死锁、无丢失更新及锁释放后可继续，不能仅证明当次等待没有超时。

本次不默认引入 advisory lock。若后续测量证明有必要，必须先覆盖所有授权/角色/状态/邮箱/归属写入口并定义统一锁序，单独更新方案；仅替换三个入口不足以保证安全。

### 5.1 S3 可选：SQL 内计算范围摘要

- 可评估对选中成员的规范化投影在 SQL 中执行 `string_agg(... ORDER BY id)` 再计算摘要（如 `md5`），Go 仅取摘要值；算法与位置不改变范围字段、顺序及鉴权合同。
- 使用无歧义的结构化/长度编码，明确 NULL、空字符串和空集合；成员摘要、部门标签及当前操作权限投影都要纳入最终版本，同一事务内生成版本和读取报表。
- RV4 若采用该优化，验证稳定排序、特殊字符、空集合、相关变更敏感和无关变更稳定，并与基准投影对照。数据库仍需扫描/聚合选中数据，记录 SQL 内存、EXPLAIN 与耗时，不能只以 Go 不再接收列表判定性能通过。

## 6. S4：错误与 API 兼容

错误码与 HTTP 状态已按设计第 8.4 节实现；业务码读取 `reason`，兼容字符串 `code`，数字 HTTP 状态不当成业务码；`departmentErrors.ts` 仅按 `REPORT_SCOPE_CHANGED` 识别范围变化，保留本地同名异常的兼容；不得用全部 409 触发报表重载。部门编辑、成员、授权弹窗分别展示业务原因，权限版本冲突要求刷新后重新确认。

首版保留“数字部门 ID 搭配组织”的报表合同；管理资源 `/departments/:id/members` 可用独立校验器处理，去掉借改参数绕过校验的代码。仅传部门 ID 推导组织属于可选后续简化，不作为本次必须变更，避免扩大兼容面。

## 7. S5：验证范围与性能

| 验证 | 要求 |
| --- | --- |
| 权限竞态 | 打开用户编辑时获取详情/版本，详情失败禁止保存；只改备注不发送 role/权限/版本，权限变更携带同一详情版本；旧窗口不得恢复全站权限，正常组合与当前版本修改成功，缺版本/冲突无副作用 |
| 生命周期 | 降级/软删除清授权、重新提权无复活；与新授权并发时结果符合事务顺序；临时停用/恢复保留既定行为 |
| 范围与导出 | 单部门忽略无关变更；相关邮箱/部门名/成员变化被发现；全站新增成员可使旧版本失效；八 Sheet、取消和行数限制保持 |
| 管理员查询 | 无部门筛选不再读取全站成员；指定部门仍正确；查询次数、EXPLAIN、相同数据前后耗时均有证据 |
| 并发重置 | 明确重置 users→订阅、计费订阅→users 的潜在反序，验证 command 费用互斥；真实 PG 验证重置 vs 余额扣费/转岗/撤权及身份状态变化，保留幂等、缓存及历史日志断言 |
| 审计触发器 | 复用 `department_repo_integration_test.go` 现有邮箱变更审计断言；修改 audit_logs 结构时必须覆盖，不另造重复测试或吞失败 |
