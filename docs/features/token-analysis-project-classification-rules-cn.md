# Token Analysis 项目分类规则

日期：2026-11-03。来源：用户在项目来源采集后的分类说明。状态：规则文档，尚未接入提取器、数据库或页面，也未执行历史回填。

采集证据：`docs/delivery/2026-11-03-project-attribution-survey/README.md`。现有实现：`docs/features/token-analysis-project-attribution-design-cn.md`。本文件定义后续分类口径，旧实现的 cwd basename 规则不代表本文件已生效。

## 分类原则

识别到明确的项目边界，就统一归到该项目，忽略项目内部的目录、模块和文件。没有足够依据确定项目边界时，使用提取到的完整文件或目录路径作为归因值，备注为“文件”。完全没有有效路径或项目证据时，保留未归因。

| 分类结果 | 归因值 | 备注 |
| --- | --- | --- |
| 后端项目 | `服务/项目`，例如 `micro-manager/activity-server` | 可留空；仓库地址单独保留为来源证据 |
| 其他明确项目 | 项目名或仓库名，例如 `WelcomeScreen`、`compass`、`xyai` | 可留空 |
| 文件或普通目录 | 规范化后的完整路径 | `文件` |
| 无有效证据 | 未归因 | 沿用现有未归因语义 |

“文件”也包含无法确定项目根的目录；不能把目录末段随意提升为项目名。上述结果是业务口径，不指定本轮新增数据库字段。

## 用户已明确的规则

| 规则 | 匹配依据 | 归因结果 | 边界 |
| --- | --- | --- | --- |
| R1 后端服务/项目 | 已知后端仓库结构中的 `micro-*/<项目>/…` 或 `microservice/<项目>/…` | `服务/项目` | 截止到项目这一层，后面的 modules、services、models、src、文件名均不继续细分 |
| R2 已明确的项目根 | 路径属于确认的项目根及其子目录 | 统一项目名 | O02 → `WelcomeScreen`；O03 同类 compass 子目录 → `compass`；O18 → `xyai` |
| R3 orig-web 仓库 | 仓库地址或本地路径含完整目录段 `orig-web/<仓库名>/…` | `<仓库名>` | 取 orig-web 后第一段；去仓库后缀 `.git`，忽略其后文件、分支/提交页面等路径 |
| R4 已确认别名/副本 | 已知 worktree、临时副本或仓库别名与正式项目对应 | 正式项目名 | O19 → `client-web-page`；O18 已列出的审核副本 → `xyai` |
| R5 普通文件/目录兜底 | 有有效路径，但 R1–R4 均未确定项目边界 | 完整文件或目录路径 | 备注固定为 `文件`；不猜测业务名称、不按用户合并 |

R1 依据用户此前说明“后端仓库都基于这个理念”，本轮以 `micro-manager/activity-server` 明确截止层级。同名项目在不同服务下分开，例如 `micro-activity/modules` 与 `micro-perm/modules`；项目内的 `battlepass/modules/…` 仍归 `micro-activity/battlepass`。

R3 与 R4 的关系：先提取原仓库名，再应用明确的别名。例如 `orig-web/orig.client-web-page.git` 最终为 `client-web-page`。用户没有要求全局删除所有仓库名的 `orig.` 前缀，因此其他 `xx` 默认保留仓库名原样；后续有明确别名再合并。

## 同类推广口径

以下是根据用户范例整理的推广办法，不声称用户已经逐项命名了原清单的全部 43 组候选。

| 情况 | 推广办法 |
| --- | --- |
| 同一已确定项目根下的不同子目录 | 全部回到同一个项目名；例如确认 `atlas` 为项目根后，deploy、manager-service、resource-service、service_sdk 均可归 `atlas` |
| 存放多个项目的容器目录 | 不把磁盘根、用户名、code、AI_project、PycharmProjects、allsite、workshop、tools、worktrees 哈希直接当项目；需要确定其下的实际项目根 |
| 尚未确定根的其他候选 | 当前按完整路径归因并备注“文件”；不能只凭某个目录名像项目就自动套用 compass 的层级 |
| 不同机器上同一已确认项目 | 可按同一项目规则归并，来源路径分别保留；普通文件兜底不自动跨机器合并 |
| 同名仓库或跨地址仓库 | 保留仓库主机与完整根作为证据；没有别名或同源依据时，不仅因显示名相同就断定同一仓库 |

## 处理顺序与证据选择

1. 从当前工作区、工作目录、仓库地址、附件（含 `tagged_files`）提取有效路径，去掉列表符号、行号和 `(85 lines)` 等外围说明。
2. 先判断该路径是否属于当前工作对象，再应用分类。依赖缓存、工具自带示例、普通文档引用、历史工作区只是辅助证据，不自动替代当前项目。
3. 匹配明确的根/别名与后端结构；`orig-web` 先取仓库名，再应用明确别名；命中后停止向项目内部细分。全部未命中才使用文件路径兜底。
4. 路径分隔符统一为 `/`；Windows 盘符统一大写、比较时忽略大小写，展示保留目录原名；POSIX 路径保留大小写。同名路径的 `.git` 去除仅用于仓库名，不能改变普通文件名。
5. 目录规则按完整路径段匹配：`compass-old` 不匹配 `compass`，`xyai-backup` 不因前缀相同就归到 `xyai`；临时副本只使用已确认的映射。

多线索选择建议（实施默认口径，非用户已确认的费用拆分规则）：优先使用当前明确工作区；附件与仓库证据归一到同一个项目时合并。若确实涉及多个项目且不能确定主项目，保留候选并继续未归因，不取文本中第一条路径、不因频次较高就归入某项目，也不把一条请求的完整 token 重复计入多个项目。

Go `pkg/mod` 等依赖缓存即使命中 `micro-*/<项目>`，也应先通过“当前工作对象”判断。单纯引用 `micro-activity/modules` 依赖不能把当前 `battlepass` 请求改归 modules。文件兜底同样不能把无关示例或缓存路径变成当前归因。

### 新归档如何自动生效

- `token_analysis_auto_index.go` 已有自动任务，启动后执行一次，再按配置间隔处理昨天和今天的新增行；`config.go` 和 `deploy/config.example.yaml` 的默认间隔为 300 秒。上线时须确认生产实际配置，不能把默认值当线上实测值。
- 开启归档、`token_analysis.index_enabled=true` 且 `auto_index_interval_seconds>0` 后，部署后的新增索引行可走新规则，无须再新增每天全量扫描的 cron。轮询间隔不是严格的可见延迟上限，大文件积压和失败会使页面延后。
- “新增索引行”按索引位置定义：升级后首次处理的旧请求也会应用新规则；已越过索引位置的历史行不会因为服务重启或点击普通“索引当前范围”而自动重新归因。
- 第一版可采用随发布交付的版本化规则集。若希望以后在后台改规则并立即生效，需要另行实现持久化配置、发布版本和实例刷新；当前没有可以直接粘贴这份规则文档的现成配置入口。

### 历史处理与性能边界

- 已有可信工作目录/路径足够判断时，直接对这些证据重新分类；线索不足的记录再按 `source_file`、行首/长度或行末偏移读取对应原文，并核对 archive_id 与正文哈希。无需默认重读全部 215 GiB 文件。
- 回填前输出候选差异与数量，保存受影响归因字段的前像；写入以读取时的版本和源记录身份作条件检查，避免覆盖并发更新。原始归档保持原样。
- 不删除全局索引水位来触发全量重灌，也不调用普通摘要 upsert 去重建净输入、风险结果或账单关联。归因专用更新不创建账单、不重新扣费。
- 只读采集已证明存在有效路径，不代表保留的精简候选证据足够对每条请求定案；需要协议上下文的记录仍须定向读原文。原文缺失或损坏且证据不足时保留未知，不补造项目。
- 后续将有效线索与规则版本持久化，规则调整可优先重算派生结果；失败重试、历史故障恢复和归档容量治理仍遵循各自机制，不能把项目分类升级当成归档 writer/索引水位故障已修复。

当前工作区包含其他功能的未提交改动，实施与发布应单独隔离本功能变更。以上是落地建议；本轮未执行代码实现、迁移、生产连接、部署或回填。
