01 / 基础认知

三个角色，各做一件事

你不需要先学完一门编程语言。先分清“在哪里操作、请求经过哪里、由谁回答”，接入就会容易很多。

UNDERSTAND
01 — CODEX

你的工作台

你在 Codex 里描述任务。它可以在获得相应权限后查看项目、修改文件、执行命令、分析报错，并整理交付结果。

你看到的：对话、文件修改和运行结果。

02 — RELAY

公司的中转平台

中转接收客户端请求，再路由给允许使用的模型；统一管理 API Key、分组、额度和使用记录。

你需要的：接入地址、自己的 Key、可用模型。

03 — MODEL

负责推理的模型

模型负责理解文字、生成方案和代码。不同模型的能力、速度、费用和工具兼容性会不同，以分组实际支持为准。

你选择的：管理员推荐的可用模型 ID。

名词可以这样理解使用时记住
平台账号登录中转网站的身份网站密码不等于 API Key。
API Key客户端调用模型的通行证每人使用自己的 Key；不放进代码仓库、群消息或截图。
Base URL模型 API 的入口地址常带 /v1；与网站首页、登录页是不同用途。
模型 ID请求时使用的准确模型名称必须与当前 Key 所属分组允许的名称一致。
Token / 额度输入、输出及相关处理的计量与限额长日志、多轮上下文和反复重跑会增加用量；以平台记录为准。
接入中转用于模型调用，不会自动开通 ChatGPT 订阅、Codex 云端任务或其他应用的授权。模型请求需要联网；本手册和后面的日志分析练习可以离线使用。

03 / 工作方式

从一句“帮我做”，变成一次完整交付

给 Codex 一个明确工作目录，把相关样本放进去。它需要知道你的材料、环境、边界和判断对错的方法。

WORK TOGETHER
01准备材料

脱敏样本、文件路径、字段说明、已有规则。

02说清结果

要脚本、报表还是网页；定义输出与验收。

03先做小样

先用十几条样本打通，再扩大数据量。

04看修改与验证

查看文件差异、执行命令和实际输出。

05收好交付物

保留源码、样本、使用说明和已知限制。

一个简单的工作目录

codex-lab/
├─ input/          原始样本，保留不变
├─ src/            生成的脚本或网页源码
├─ output/         生成的报表与结果
├─ tests/          必要的验证样本或测试
└─ README.md       安装、运行、字段与限制

第一次练习可先用一个空文件夹。对已有项目，先让 Codex 阅读项目规则和入口，了解现状后再动手。

用“反馈事实”推动下一轮

有效反馈：“样本 12 条，脚本只统计 11 条；第 7 行是空设备名，请拒绝处理并标注行号。”

还不够明确：“不对”“不好看”“你再优化一下”。

遇到报错，把执行命令、完整报错和预期结果一起提供。对方才能定位原因，而不是反复猜测。

让 Codex 报告“实际运行了什么、实际看到了什么、还有什么未验证”。生成了代码和验证了代码是两个不同阶段。

05 / 任务提示词工作台

写清六件事，结果更接近预期

目标 → 材料 → 环境 → 交付 → 边界 → 验收。下面会根据你的填写生成一段可以复制的完整任务，所有内容只在本页处理。

PROMPT WORKBENCH
将目录、字段和验收值换成你的实际情况。不要在这里填写密码、Key 或真实客户敏感数据。


后续追问也有模板：解释、报错、检查、交接
解释一段代码
请面向零基础同事解释这个脚本：输入是什么，输出是什么，从哪个函数开始，数据经过哪些步骤。用一条样本演示每一步，标出哪些操作会写文件或访问网络。暂不修改代码。
带着事实定位报错
执行命令：[粘贴原命令]
运行目录与版本：[补充路径、系统、Python/Node 版本]
完整报错：[粘贴已脱敏的终端输出]
预期结果：[说明应该怎样]
实际结果：[说明当前怎样]
请先定位根因，再做最小修改。保留原始输入，运行对应验证，解释修复依据和未覆盖的情况。
交付前检查
请检查本次修改是否满足原始需求：计算口径、异常输入、超时与重试、文件覆盖、敏感信息、资源消耗。列出有证据的问题及位置，不为了凑数提建议。汇总实际运行命令、结果、未验证项，并补全 README 的使用步骤。

07 / 利用好生成的代码
代码生成之后，接下来做什么

USE THE CODE

进阶：什么时候需要在你写的程序里调用中转 API？
用 Codex 帮你写程序：模型调用由 Codex 完成；日志统计、固定公式报表等程序写好后通常可以自行运行，不需要每次再调用模型。
你的程序本身需要 AI：例如每次收到工单都要生成摘要，才需要在程序中调用中转 API。把 API Key 放在服务端环境变量，前端网页通过自己的后端调用；不要把 Key 写进可分发的 HTML 或浏览器脚本。
需求优先实现方式验收重点
汇总、排序、去重、固定公式普通代码按明确规则计算相同输入产生相同结果；可对账。
文本归纳、分类、知识问答程序按需调用模型，保留输入来源抽样检查、异常与限流处理、费用预算。
对生产系统执行操作独立权限校验、执行日志与明确确认模型建议与最终执行分开验证。

路线 A · GitLab：克隆 → 功能分支 → Codex 修改 → MR 审核


  1. 把已有 GitLab 项目克隆到自己的工作目录
    安装 Git 后，在 GitLab 项目页的 Clone / Code 区域复制 HTTPS 或 SSH 地址。按公司方式完成身份验证，不把密码或访问令牌嵌入 URL。第一次下载可以执行：
    首次下载 · 仓库地址为示例
    git --version
git clone "https://gitlab.example.com/network/network-portal.git"
cd network-portal
git status --short --branch
git branch --show-current
    已经有这个项目时，直接进入现有目录，运行最后两条检查命令。若存在未提交修改，先让 Codex 列清文件和差异，确定是否属于本次需求；无法分开时，在另一个新目录克隆，保留原工作区。
    2. 

  2. 从确认过的基线创建功能分支
    以下假设负责人确认基线是 dev，工作区没有未提交修改。若实际为 main、master 或其他分支，替换命令中的 dev。示例功能号 10001 也应替换为团队分配的编号。
    干净工作区 · 从 dev 开始
    git fetch origin
git switch dev
git pull --ff-only origin dev
git switch -c feature/hy/10001_device_search
git status --short --branch
    每条命令成功后再执行下一条。若快进更新失败或同名分支已存在，先检查原因，不执行强制重置。新增功能分支使用 feature/hy/10xxx_XXX；问题修复使用 hotfix/hy/0000_XXX，按实际任务类型命名。
    3. 

  3. 让 Codex 打开这个本地目录
    桌面应用添加 network-portal 项目目录；VS Code 用“打开文件夹”；CLI 则在该目录运行 codex。先发送下方共用的“只读接手”提示词，再发送实现任务。GitLab 网页链接可作背景，实际代码工作以本地目录为准。
    4. 

  4. 验证完，先看差异，再决定提交
    在项目根目录执行下面的只读检查。git diff 不显示未跟踪文件的正文；对 ?? 文件要单独打开检查。已暂存内容用 git diff --cached 查看。
    本地检查 · 不会推送代码
    git status --short
git diff --stat
git diff --check
git diff
git diff --cached
    与需求无关的改动、凭据文件、运行日志和构建产物不应混入本次提交。构建成功之后，还要按下方验收表检查页面实际行为。
    5. 



代码已审核且明确允许提交后：提交、推送并创建 Merge Request
只暂存确认过的文件。下面的带中文文件路径需要替换；不应把命令原样当作实际文件名使用。
这些操作会创建提交并写入 GitLab
git add -- "实际修改文件1" "实际修改文件2"
git diff --cached
git commit -m "feat: add device name search"
git push -u origin feature/hy/10001_device_search
在 GitLab 创建 Merge Request（合并请求，简称 MR）：源分支选本次功能分支，目标分支选负责人确认的基线（此例 dev），填写需求、变更和验证结果，指定审核人。跟进 CI 检查与审核意见，修正后推送到同一分支。推送成功不代表已经合并；合并与部署仍按团队流程执行。





路线 B · SVN：检出工作副本 → 更新基线 → Codex 修改 → 审核提交


  1. 检出负责人指定的代码路径
    安装 SVN 客户端。Windows 同事可使用 TortoiseSVN：在空目录右键选择“SVN Checkout”，填写实际 URL。以下命令展示同一操作；教学路径采用 trunk，实际若要求在功能分支开发，就使用已分配的 branch URL。
    首次 checkout · SVN URL 为示例
    svn --version --quiet
svn checkout "https://svn.example.com/svn/network-portal/trunk" network-portal-svn
cd network-portal-svn
svn info
svn status
    已有工作副本时直接进入目录，从 svn info 核对 URL，再看 svn status。状态为空通常表示没有本地变更；M 是修改、? 是尚未纳入版本控制的文件。保留已有改动，不直接执行全目录 revert。
    2. 

  2. 从干净工作副本同步基线
    确认路径正确且已有修改得到处理后，再更新：
    修改前更新 · 记录工作路径和版本
    svn update
svn status
svn info
    记录实际 URL、更新结果及版本信息。若出现 C 或树冲突，先处理冲突再开发。SVN 分支通常是服务器上的目录，不使用 git switch；需要新分支时，按团队流程创建或由负责人提供路径。
    3. 

  3. 在工作副本中使用 Codex
    用 Codex 桌面应用 / VS Code 打开 network-portal-svn，或在该目录运行 codex。明确告知“这是 SVN 项目”；不要让它执行 git init、删除 .svn，或把整个工作副本改造成 Git 项目。
    4. 

  4. 检查变更与新文件
    本地检查 · 不会提交到 SVN 服务器
    svn status
svn diff --summarize
svn diff
    svn diff 不包含 ? 新文件的正文，需要单独打开审核。确认需要纳管的新文件才执行 svn add；不把依赖目录、编译输出和本地凭据一起加入。
    5. 



代码已审核且明确允许提交后：选择路径，直接提交到服务器
提交前与仓库同步，若产生冲突，先人工确认合并结果并重新验证。TortoiseSVN 可依次使用 SVN Update、Check for modifications / Diff、Commit，在提交窗口仅勾选本次需求相关路径。
逐步执行 · 路径需替换
svn update
svn status

# 有冲突时到此停止，解决后重新运行项目验证
# 仅当确有已审核的新文件时，才执行下一条
svn add -- "实际新增文件路径"
svn diff

# 按团队要求完成审核与验证后，再提交指定路径
svn commit "实际修改文件路径" "实际新增文件路径" -m "feat: add device name search"
svn status
没有新文件时省略 svn add，提交命令中也去掉该路径。svn commit 成功就已经写入服务器，不存在之后再 push 的步骤。记录服务端返回的修订号（如 r12345，仅为示例），用于需求关联与交接。SVN 不自带 GitLab MR 流程，应在 commit 前按团队要求完成评审；提交也不等于部署。

10 / 常见问题
先看现象，再找原因
错误信息只是线索。提供发生时间、客户端版本、模型 ID、脱敏报错及请求 ID（若有），能帮助管理员更快定位。
TROUBLESHOOTING


现象优先检查下一步
网站能开，Codex 不通API Base URL、客户端配置位置、API Key、分组是否允许 Codex。用平台对应 Key 的「使用」说明核对；网站登录成功不等于 API 鉴权成功。
401 / 鉴权失败Key 是否正确、过期或撤销；环境变量是否传给当前进程。不要输出 Key 全文；核对变量是否存在、配置方式是否混用。
403 / 无权限分组、模型或客户端限制，IP 策略以及网关返回的具体信息。向管理员确认权限与策略，不反复更换身份尝试绕过。
404 / 模型不存在是否重复 / 缺少 /v1，模型 ID 是否允许，端点是否匹配。从平台配置重新复制准确地址与模型名称。
429 / 配额相关错误并发或速率限制、余额、订阅日额度与可用容量。减少并行任务，按提示稍后重试；额度问题按部门流程处理。
超时、连接失败、5xx本机 DNS / 代理、网络可达性、网关与上游服务状态。保留时间和错误信息；避免密集无限重试。
能回复，但不会操作文件是否打开正确工作目录、文件权限、模型工具兼容性、当前审批模式。先做小范围文件读取验证，再按任务需要调整授权。
代码运行报错工作目录、文件名、依赖版本、输入格式与完整错误堆栈。使用前面的报错模板，把可复现信息交给 Codex。


网页里能聊天，为什么还要用 Codex？
Codex 的价值在于围绕工作目录持续处理文件、修改代码和执行验证。只需要解释一个概念时，聊天已经足够；需要完成一个可运行成果时，工作目录与工具执行能减少来回复制。
我完全不懂代码，能直接使用生成的程序吗？
从离线样本、小范围任务开始，要求生成完整运行步骤和可人工核对的结果。涉及真实设备、客户数据或生产变更的程序，由具备相应经验的同事复核后再使用。至少先弄懂输入、输出、写入位置与访问范围。
中转是不是意味着材料只留在公司？
不能这样理解。模型请求会经过中转，通常还会转发到上游；中转是否记录请求取决于实际配置。文件片段、提示词和工具输出也可能作为模型上下文发送。只使用公司允许处理的数据，必要时先脱敏；本机的某个“存储关闭”设置不代表所有链路都不留存。
没有结果时，是否应该不停点重试？
先判断是网络、鉴权、额度还是任务本身的问题。重复请求可能增加负载和费用，也可能重复执行已完成的操作。查看客户端输出和平台记录后，再决定是否重试。
如何向管理员描述“接不上”？
提供：发生时间、系统与 Codex 版本、使用入口（桌面 / 扩展 / CLI）、已脱敏的 Base URL、模型 ID、Key 名称或末几位、错误码和请求 ID（若有）。不要发送完整 API Key、认证文件或未脱敏日志。
