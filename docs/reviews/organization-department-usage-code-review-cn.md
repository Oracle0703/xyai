## 保留的必要约束

| 机制 | 保留原因 |
| --- | --- |
| 操作者与成员 `users` 行锁 | 与撤权、停用、降级、删除、转岗和邮箱更新串行；仅靠查询条件无法关闭鉴权与重置间隙 |
| 单项订阅 `FOR UPDATE` | 仓储仍支持修改订阅所属用户；必须保证校验目标与实际重置目标一致 |
| 新增授权部门 `FOR SHARE` | 阻止检查启用状态后、插入授权前部门被停用；只移除保留授权上的重复锁 |
| repeatable-read 查询 | 保证权限、成员、分页/嵌套用户和返回版本来自同一读取快照 |
| 成员/授权 CAS 与原子审计 | 防止旧窗口覆写并发变化，保证审计与业务同成败；239/240 迁移及触发器不改写 |
| 幂等预检、事务内复核和提交后缓存失效 | 分别保护缓存重放、真正写入及缓存一致性，不能合并成一次锁外检查 |
| 负责人无 grant 拒绝、两种错误信封适配 | 无授权不得退回全站；服务端确实存在数字 code + reason 与字符串 code 两种错误格式 |
| 不带管理身份的仓储内部调用 | 网关计费和普通用户读写仍使用原合同；管理 HTTP 入口必须经过认证中间件，不把内部调用当作管理授权 |

本轮没有新增锁协议、advisory lock、迁移或配置开关。计费 command 费用二选一及潜在的混合扣费锁序风险仍按既有设计处理。
