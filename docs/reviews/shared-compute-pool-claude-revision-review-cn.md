## 一 结论

**第四方案方向合理，是当前更值得验证的轻量动态方案；当前稿还不能按 84 分直接进入正式实施。** 它绕开了池级绝对容量换算，但把业务政策改成了按账号百分比限制高用量组。它不自动满足原先“普通组七天用量 × 1.05”的动态保底，也不保证普通组并发。

建议保留该路线，先补齐角色保护与原账号策略的组合规则、数据过期处置、真实准入覆盖和刷新写回，再做观察模式试点。需要强资源隔离时，方案一的配置子集仍更稳妥。

## 二 必须修正的主要问题

### F1 过期放行没有一批请求的消耗上界

严重度：P1。HTML 第 49、77、116、177、203–209、278 行。

文稿把快照过期后的 fail-open 描述为“一批在途请求的有界泄漏”。但源码 `resolveOpenAIQuotaUtilization` 在快照陈旧时只返回无有效暂停信号，没有实现单次探测令牌、共享放行次数或放行消耗预算。`updateCodexUsageSnapshot` 在缺少响应头快照时直接返回，且存在 30 秒持久化节流及异步写库；失败请求、缺少额度头、写入失败或持续旧缓存都可能让后续多批请求继续进入。

HTML 自己的 `highRequest` 也只是把每次越线放行量写成 20，并不限制总次数。离线反例：从剩余 200 开始，连续执行 10 次过期状态放行，剩余降到 0、累计消耗保护区域 200。页面默认“额度数据过期”场景中的 `leaked` 从第 0 到第 14 步始终为 0，没有展示它声称已说明的越线风险。

源码证据：

- `backend/internal/service/openai_gateway_scheduling.go:670`：过期/重置返回无暂停信号。
- `backend/internal/service/openai_gateway_service.go:66`：快照写入最短间隔 30 秒。
- `backend/internal/service/openai_gateway_usage.go:1174`：空快照、节流与异步写回。
- `backend/internal/service/concurrency_service.go:373`：非正并发配置还会免除本地槽位限制，不能假设固定批次上界。

修正建议：高用量角色的保护信号过期或未知时，优先采用保守拒绝并由后台主动刷新；如果确需探测放行，单独设计有租约、次数/并发及消耗限制的探测机制。即使改为保守拒绝，已有在途请求和新鲜快照的采样延迟仍可能产生追加消耗，不能承诺绝对不越线。

### F2 提高阈值来增加普通组保留量的方向相反

严重度：P1。HTML 第 118 行。

文稿在“普通组粘性集中、保留可能不够”时建议“提高 T”。按其定义，高用量只使用 `used% < T` 的账号。T 从 80% 提高到 90%，高用量组能继续消耗的范围扩大，名义剩余从 20% 减少到 10%，与增加普通组保障的目标相反。

修正建议：如果意图增加名义保留，应讨论降低高用量阈值；但普通组自己已耗尽粘性账号时，调整阈值也不能创造容量。需要检查普通组可迁移账号、模型覆盖和会话约束。不可迁移 continuation 不能为了均衡而随意切号。

### F3 只向上下文注入阈值不能保证生效

严重度：P1。HTML 第 47、61、103 行。

现有阈值解析优先读取账号 `extra.auto_pause_7d_threshold`，只在未设置时回退上下文默认值。若仅把角色阈值放入既有默认设置，一个账号已有 95% 覆盖就可能使高用量组的 80% 不生效。逐窗口 `auto_pause_7d_disabled` 还会跳过检查；自动用卡存在“有可用卡则返回不暂停”的提前放行分支。当前方案没有明确这些策略的组合顺序。

源码证据：`backend/internal/service/openai_gateway_scheduling.go:527`、`:547`、`:563`、`:612`。

修正建议：把高用量角色保护定义成额外的更严准入条件，与原账号健康/额度/人工停用取交集；不改写共享账号全局状态。明确原账号豁免仅针对原机制，还是也能豁免角色策略；自动用卡可正常运行，但未经新鲜额度确认不能绕过角色保护。重置成功后再重新判断。更严的原账号规则也不能被角色阈值放宽。

### F4 覆盖表将多平台和不同选号路径概括为自动覆盖

严重度：P1。HTML 第 95–100 行及第 61 行。

`shouldAutoPauseOpenAIAccountByQuota` 在 `!account.IsOpenAI()` 时直接放行，不会因为上游 handler 调用了 `CheckBillingEligibility` 就自动覆盖 Gemini、Grok 或 Anthropic。文稿列举的 prompt-too-long 兜底实际是 Antigravity 请求回退到 Anthropic 分组；这不能证明 OpenAI 的角色阈值自动覆盖该路径。即使同为 OpenAI，也存在 scheduler 与 legacy 等入口，不能统一声称它们都经过 `selectAccountForModelWithExclusions`。

源码证据：

- `backend/internal/service/openai_gateway_scheduling.go:521`：平台 guard。
- `backend/internal/handler/openai_embeddings.go:128`：走 `SelectAccountWithSchedulerForCapability`。
- `backend/internal/handler/gemini_v1beta_handler.go:507`：Gemini 走另一套 gateway 选号。
- `backend/internal/handler/gateway_handler.go:993`：兜底目标要求 Anthropic。
- `backend/internal/handler/openai_gateway_handler.go:2851`：WS 后续轮次需额外接入，Claude 此项判断正确。

修正建议：首期明确为具备有效周额度快照的 OpenAI 账号，列出 HTTP、legacy/scheduler、sticky、选中复核、同账号重试与 WS 逐轮的实际调用合同。其它平台和 Live/媒体持续消耗路径列为未覆盖或后续范围。保护身份不能因内部 fallback 换成普通组而自动解除；需要明确原调用方角色与目标资源策略如何组合。

### F5 第四方案没有实现原公式 其离线校准仍依赖容量

严重度：P2。HTML 第 41、104、138 行。

“人工设定每账号 80% 阈值”确实可以不换算绝对容量。但是文稿随后给出 `T ≈ 1 − R / 池周容量`，这里仍需要和 R 同单位的容量。不能同时把“无换算依赖”和“已按 R 校准”作为已成立优势。

第四方案的更准确描述是：**改变高用量组对账号剩余区间的访问权限**。这是有价值的替代政策，但与“严格动态保留普通组七天需求 × 1.05”不是等价实现。普通组的实际可用区间还受自己的账号阈值、当前消耗、模型支持和在途请求影响，不总是可用 `(1−T)` 的整段额度。

修正建议：首期 T 由运营按普通组完成率、限流、分布及实际可用账号观察调整；明确未承诺原公式。要将 R 用于量化校准，另行建立有置信边界的换算，且不把价格表费用当作天然的上游额度单位。一个周周期可用于初步观察，但不能保证拟合稳定；池外消耗、模型配比、早期重置与价格变化会干扰关系。

### F6 演示仍用全池停止线模拟逐账号阈值

严重度：P2。HTML 第 173、182、190–218、221 行。

第四方案实际创建的还是 `shared` 总量和 `stop=200`，没有账号列表、各账号 `used%`、不同容量和各自重置时间。仅把恢复事件改名为“甲/乙账号重置”，不足以验证逐账号控制。

反例：两账号各容量 500，一个已用 100%，一个已用 70%。总剩余 150。真正的 T=80% 规则允许第二个账号再使用约 50；当前演示因为总剩余 150 小于全池停止线 200，直接暂停。即使账号容量相同，只要消耗分布不同，池级替身也不等价。

修正建议：为方案四使用至少三个账号对象，分别显示容量、已用比例、重置时间与各角色是否可选；分别演示偏斜消耗、重置、无信号及正在执行的请求。将“数据过期”场景改为在账号已经越线后发生，才能呈现真实取舍。当前“预计重置直接放行”和“预计到达但未确认时不放行”的通用说明还需按方案分别标注，避免互相矛盾。

### F7 查询成功并不等于调度快照已更新

严重度：P2。HTML 第 48、135 行。

`OpenAIQuotaService.QueryUsage` 主要查询并返回 payload，不会直接完成通用额度字段和调度缓存的写回。普通账号的管理端使用统计还存在 `probeOpenAICodexSnapshot` 路径；直接额度 GET/refresh 也不是只经 `AccountHandler.GetUsage/GetUsageBatch`。因此“在 QueryUsage 上加节流即可”少了持久化、版本与调度可见性的合同。

源码证据：`backend/internal/service/openai_quota_service.go:146`、`:214`；`backend/internal/service/account_usage_service.go:721`；`backend/internal/handler/admin/openai_oauth_handler.go:486`、`:513`。

修正建议：后台任务完成查询、规范化、较新快照校验、写回、缓存可见和失败退避的完整链路；不要让新主动查询结果被迟到响应头覆盖。可复用现有工具函数，但不能把查询返回直接视为保护服务已看到新状态。

## 五 第四方案建议收敛版本

1. 首期只覆盖具备可信 7d 快照的 OpenAI 周额度账号和约定的文本 HTTP/WS 入口。5h、其它平台、Live/媒体持续消耗另列范围。
2. 角色限制作为额外 gate，与原健康、账号阈值、人工状态取交集；不改共享账号 `schedulable`，不通过放宽账号阈值让普通组绕过原限制。
3. 高用量阈值由配置管理。降低 T 才会扩大名义保留段；没有同单位容量时不宣称该 T 满足七天需求公式。
4. 缺失/陈旧/待重置确认的角色保护数据，默认阻止高用量在该账号上发起新请求；后台主动刷新可用状态。普通组继续执行原有规则。
5. 在候选和选中复核处复用同一判断；明确重试的策略身份；WS 每轮读取新鲜账号与角色配置，越线后按协议结束该连接或轮次，不悄悄换掉不可迁移账号。
6. 后台查询、写回与调度缓存形成闭环，防止旧结果覆盖新结果；错误分类独立，只有确实因角色过滤无候选时才返回对应本地限流原因。
7. 先观察模式，再小范围拒绝；关注普通组完成率、等待、可用账号分布、高用量追加消耗与恢复时间。需要并发预留时另行设计。
