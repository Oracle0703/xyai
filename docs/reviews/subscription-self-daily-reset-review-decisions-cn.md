# 自助日重置：两份审核意见裁决清单

日期：2026-09-22。范围：设计复核，不实施自助重置，不修改两份审核原文。

后续状态：本清单的技术建议已合入 `docs/features/subscription-self-daily-reset-design-cn.md` v2；下表保留初稿审核快照。#3 已按后续反馈澄清为两种可行读取时序，不认定 A 的事务外 GetValue 与禁进程缓存要求相互矛盾。

2026-09-23 更新：用户授权决定日卡范围，已在原设计 v2.1 定稿为“首版排除一次性日卡自助重置、不增加开关、管理员仍可重置”。下方 #6 等“待产品决定”描述保留为当时审核记录，不再是当前阻塞项。

**结论：保留原设计的独立模块、附属计数表、同事务扣次和提交后缓存失效。日期采用第一份的 DATE＋日历字符串；补充第二份的重试分类和跨实例缓存要求。两份审核存在共同误判，不能把全部 P0/P1 原样采纳。**

## 一、存在分歧或不能原样采纳的意见

| # | 两份意见与冲突判断 | 最佳建议与依据 | 闭环条件 |
| --- | --- | --- | --- |
| 1 | **真实选型分歧。** A/P0-3 保留 DATE、绑定字符串；B/必须写死①首选 `quota_day_start timestamptz`，也接受 DATE＋字符串 | **采纳 A。** 业务标识是自然日，保留 `quota_date` 最直接。Go 按服务端时区产生 `YYYY-MM-DD`，读写都按日历值，不做时区转换；不用数据库 `CURRENT_DATE` 推算。TIMESTAMPTZ 也能正确实现，但不是必须改表的理由。[E1] | 可：UTC 数据库会话＋上海业务时区，覆盖 23:59、00:30、08:30，并验证同一天不会恢复已用次数。实际 PostgreSQL 验证仍待实施 |
| 2 | **两份共同过度断言。** “time.Time 写 DATE 必经 timestamptz 转换并在凌晨错日”没有给出实际 SQL/绑定复现 | **保留风险，撤回必现结论。** pq 实际编码保留 `+08:00`，SQL 参数类型和转换路径决定结果；不能仅由 DATE 类型推出错日。允许 `YYYY-MM-DD` 参数的显式 `::date`；禁止的是依赖会话时区从时间戳推导业务日期。若绑定的是当天零点而非当前时刻，错误强转也未必只影响 00–08 点。[E1] | 可：把字段、绑定、读取和比较方式一起写死；不能以本轮驱动编码检查代替数据库转换测试 |
| 3 | **读取时序有不同选项，A 两项建议不矛盾。** 开事务前普通 GetValue 与“不读进程缓存”可以同时成立；A 的池耗尽推断也有并发前提 | **保留事务内选型，撤回对 A 的矛盾定性。** 在 AtomicSuccess 事务内、取订阅锁之前，用同一事务 executor 读完整组织策略；取锁后再读当前归属并选择上限。事务已占连接后禁止再走普通 Get/GetValue；事务外先读是另一种可行方案。[E2] | 可：连接池限制为 1 时也能完成；新请求使用新策略，在途请求按本次读取快照完成；不增加全站锁 |
| 4 | **产品建议不同，不是设计自相矛盾。** A/P1-3 把“尚未确认改选”解释成“尚未选定”；B 建议改用户共享 | **保留每订阅独立计次。** 用户已明确选过独立计次，随后询问共享的利弊不等于改选。按组织配置也不能证明权益一定是员工福利。共享是否更合适是产品判断，不能据此覆盖已有选择 | 已有明确口径：A、B 两个订阅各有 N 次；只有用户明确改选后才更换计数主键，不重复索要同一确认 |
| 5 | **拒绝演进结论。** A/P1-3 称加冗余 user_id 后改共享只需唯一索引；B 也建议预留此列 | **不为假设中的切换加字段。** 同一用户有两条订阅计数，直接增加 `UNIQUE(user_id)` 就会冲突；当天已用次数仍需汇总、归并和确定折算规则。现有订阅本来就含 user_id，可关联取得。[E3] | 可：第一版只支持独立模式。未来另做迁移设计；冗余列不能代替数据迁移，更不能消除当天权益折算 |
| 6 | **真实权益取舍，不能直接定为已确认漏洞。** A/P0-1 称日卡“永久增发、单价五折”；B 更准确地按是否属于预期权益判断 | **采纳 B 的条件判断；建议第一版日卡不开放自助，但留给用户裁定。** 源码只证明它不自动刷新，不能证明销售定价合同。手动清零确会增加可用量，但仍受有效期、周/月限额约束；跨自然日还可能各获得一次机会，不能简单称为永久或固定五折。[E4] | **待产品决定。** 若不开放，status/POST 同时返回 `ONE_TIME_QUOTA` 且不扣次；若开放，必须把跨日机会、到期边界和权益说明写明。现阶段不自动增加商品开关 |
| 7 | **B 的条件建议，不构成两份技术冲突。** B 建议仅内部开放时将 other 默认值改 0 | **保持原默认三类均为 1。** 用户要求默认每日一次，并未限制只对内部员工。other 是其余邮箱集合，不等于已确认的“外部付费买家”；管理员可以配置为 0。[E5] | 可：迁移初始值、管理表单和服务端规则一致；若用户决定只给内部组织，再明确改 other 初始值 |
| 8 | **共同事实错误。** A/§4.3、B/接口权限均称后端模式“关闭时”拦截用户 | **改为开启时拦截非完整管理员。** 源码在模式关闭时直接放行；开启时只让 `role=admin` 通过，子管理员也会被拦截。[E6] | 可：普通用户/子管理员/完整管理员 × 开关两态；此错误与组织禁用提示分开 |
| 9 | **共同误判为硬约束。** A/§6.2、B/接口权限要求静态路由必须先注册，否则当成 ID | **仅保留为排版惯例，不作为正确性门禁。** 当前 Gin 按 HTTP 方法分树，匹配时优先静态节点。实测两种注册顺序、用户与管理路由共 8 项全部正确命中。[E7] | 已完成路由机制核验；落地仍测真实路由注册和鉴权，不靠顺序替代测试 |
| 10 | **与用户明确 UI 要求冲突。** A/§4.6 建议移到进度条；B 承认可保留续费后并验收窄屏 | **采纳 B 的保留方案。** 按用户要求放在续费后，用换行、间距及窄屏布局解决拥挤。没有截图实测不能说“必然拥挤”，换位置也不能证明风险消失。[E8] | 可：窄屏、长名称、英文、禁用和处理中状态验收；需要改变位置时再作为产品变更讨论 |
